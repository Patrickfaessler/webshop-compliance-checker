# 09 Testing

Status: draft

## Test corpus (T-1)

`testcorpus/` holds small static HTML cases (one rule, one page each). Whole-shop tests: see T-3 test shops; a WooCommerce test shop (Docker) follows when virtualisation is available.

- Per rule at least 3 cases with a deliberately planted defect and 3 clean counter-examples.
- Each case is a folder: `index.html` (and more pages if needed) and `expected.json` with the expected state per rule.
- Format and example: `testcorpus/README.md`.

## Test shops (T-3)

Three fictional, multi-page shops in `testshops/` test the whole flow: crawl, rules, score, report. They are published on
GitHub Pages so anyone can scan them through the real app (no SSRF exception), and served locally by an automated test.

| Shop | Path | Purpose |
| --- | --- | --- |
| Teehaus Bergkristall | `teehaus/` | exemplary: no planted accessibility defects, complete legal pages |
| Radwerk Alpin | `radwerk/` | many planted defects on several pages (every implemented rule fails) |
| Seifenmanufaktur Lavendel | `seifen/` | mixed: a few subtle defects, the rest clean |

- Each shop has `expected.json`: the expected state per rule and the list of planted defects (page, rule, what). Legal
  defects are planted already and documented for the R-rules that are not implemented yet.
- Every page says it is a fictional test shop, uses invented company data, carries `noindex`, sells nothing and loads no
  real third-party trackers.
- Shops never link to each other, so a crawl stays inside one shop although all share one host.
- The pages are generated by `testshops/gen` (Go) so every planted defect is visible in one place; the generated HTML is
  committed and is what gets published.
- Automated: `backend/internal/e2e` serves `testshops/site` locally, crawls each shop in the browser and compares the
  rule states with `expected.json` (skipped without a browser).

## Metrics per rule (T-2)

| Metric | Definition | MVP target |
| --- | --- | --- |
| Recall | found defects / planted defects | ≥ 90 % |
| Precision | real defects / reported defects | ≥ 90 % |
| False alarms | reports on clean counter-examples | ≤ 10 % |
| Algorithm share | decisions without Claude | ≥ 85 % (R-rules, D-7) |
| Runtime | 50 pages, reference env | < 5 min (N1) |

## Levels

- Go unit tests per rule package; table-driven, each test names its spec ID in a comment (`// Spec: A6-1`).
- Database tests (PostgreSQL store, migrations) run only when `TEST_DATABASE_URL` is set and are skipped otherwise, so the suite runs without any database (ADR-5). Never point it at the shared project database: tests may truncate tables.
- Corpus runner: `go test ./... -run Corpus` loads all cases, runs the engine with a **fake LLM**, compares with `expected.json`, prints the metrics table.
- Flutter widget tests for the report, detail view and disclaimer (N3).
- SSRF tests: table of internal addresses, redirect chains, DNS-rebinding stub.
- Fix check: apply the template fix to the planted case, re-run the rule, expect `passed`.
- Self-scan in CI: the built Flutter app is scanned with A1–A6 (N7).
- Field test: 10 real shops in the Salzburg region compared with a manual review; willingness-to-pay survey is separate from functional testing.

## CI gates

Every push: `go vet`, `go test ./... -cover` (≥ 70 %), `flutter analyze`, `flutter test`, corpus run. A drop of recall or precision below the targets fails the build.
